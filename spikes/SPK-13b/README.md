# SPK-13b — Why the Mac and Linux builds of seven artefacts differ

Follows [SPK-13](../SPK-13/README.md), which left one fact open. At `contracts/` 90b4974f, with the
same `Scarb.lock`, Scarb 2.19.4 and one thread (`RAYON_NUM_THREADS=1`), each machine was stable
alone, but 7 of the 51 artefacts differed between the Mac (macOS arm64) and the VPS (Linux x86_64).
They fell in two groups: (a) the `Registry` class and the five artefacts that contain it, and
(b) `grimworld_logic_integrationtest.test`. This spike is a report: it changes no contract, CI
setting or pin.

## The answer

**The absolute path of the build, not the platform.** The compiler names a closure's type after
the absolute path of its source file, `{closure@<absolute path>/contracts/logic/src/types/passive.cairo:458:22: 458:85}`,
and derives the type's id from that name: `ut@[id]` with `id = starknet_keccak(name)` (checked by
`closures.py names` on the Registry class). The id is a type of the Sierra program, so the path
reaches the program itself, its text and the class hash. An artefact differs between two builds
exactly when it holds a closure type:

| Artefact | Closure types (source of each, under `contracts/`) |
|---|---|
| `grimworld_persistent_Registry` and its two test-build copies | `logic/src/types/passive.cairo:458` (the `within` closure of `assert_contributions`) |
| `grimworld_persistent` (program) | the same |
| `grimworld_persistent_unittest.test` | the same |
| `grimworld_persistent_integrationtest.test` | the same, and one generated by the test macros in `persistent/tests/test_build.cairo:948` |
| `grimworld_logic_integrationtest.test` | the same, and two generated by the test macros in `logic/tests/test_combat.cairo:251` and `logic/tests/test_lifecycle.cairo:20` |
| the other 44 artefacts (`logic_unittest.test` and the `grimworld_logic` program included) | none |

Groups (a) and (b) are one cause. Group (b)'s package does not depend on `grimworld_persistent`,
but it reaches the same closure in `grimworld_logic`, which `grimworld_persistent` depends on.

## The two hypotheses

| Hypothesis | Status | Evidence |
|---|---|---|
| **Path**: the absolute build path changes the output | **Confirmed** | four VPS paths give four sets of the 7 texts (1); the Mac's two paths give two (t-0013); the path is in the closure's name, and the closure's id is the keccak of that name |
| **Platform**: something else differs between macOS arm64 and Linux x86_64 | **Refuted for these 51 artefacts** | with the path normalised, the 7 texts are equal on both machines (2), and a Linux build with the Mac's root gives the Mac's measured sha256 (3). The other 44 artefacts were already equal in SPK-13. A literal equal path was not built (4) |

## What changes with the path

Measured on the VPS between its paths (table above), and on the Mac by t-0013:

- **Change**: the file bytes and file sha256, the Sierra text sha256 and the class hash (of the
  three Registry copies). Example: Registry JSON 673,897 bytes at `mac52` and 674,577 at `wt`.
- **Do not change**: the Sierra felt count (Registry 10,665 at every path), the number of
  `withdraw_gas` statements, the CASM felts (24,611) and the CASM sha256 (`9eaca75f52b3`). The id is
  one felt at any path length, and the path does not reach the CASM. This agrees with SPK-13: the
  Mac and the VPS had equal Registry CASM while their texts differed.

## What this means (not acted on here)

- A class hash is reproducible from a commit **at a given absolute path**: one thread (SPK-13) and
  the same root. A deployment record (D-154 §4) needs the build's root path besides the commit,
  the Scarb version and `RAYON_NUM_THREADS`, or a build from a fixed root (for example a container
  that always mounts the repository at one path).
- On macOS, `/tmp/x` builds as `/private/tmp/x`: to match a Linux build, the Mac must use a root
  that its compiler does not rewrite.
- Only artefacts with a closure type are affected; today that means the Registry and the packages
  that reach `assert_contributions`. Any new closure in contract code puts that class in the same
  position.
- Upstream: the absolute path entering a type id looks like a reproducibility bug of the compiler
  (SPK-13 cites starkware-libs/cairo#10358, an absolute-path bug fixed earlier). Not searched or
  filed here: the stop rule.
