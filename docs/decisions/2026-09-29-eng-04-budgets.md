ENG-04 implemented `register`, `create_adventurer`, `delete_adventurer` and `set_account_owner` on `Hub`.
Their storage writes match ENG-01 §9.3 exactly (counted by tests, confirmed on the local node). Their
gas is over ENG-01 §10's targets, which were estimates of computation. Figures are worst cases in L2
gas: local-node receipts, or (E) from snforge deltas; the local node's fixed part (1,006,080) is
higher than §10's Sepolia floor (816,939).

| `delete_adventurer`, two list pages | 1,731,242 (E); 1,555,840 measured at the MVP's 3 slots | 9 reads (the ownership check 3, D-33's emptiness checks 3, the record, 2 list pages), 4 overwrites | 1,150,347 | **1,750,000** |

Nothing is left to remove without changing a rule: every read is a check design/03 or ADR-0007
requires, or a word the entrypoint changes, and none is unpacked. The one lever is design-level: a
"pack empty" summary in `AdventurerCore` would save D-33's three emptiness reads (about 66k) at the
price of a frozen layout. Deleting an adventurer and handing over an account are rare; neither is
in the expedition's cost (S1).

**Recommendation:** accept the four proposed targets, written into ENG-01 §10 by ENG-04's merge, and
a **standing rule** so that implementation tasks do not escalate every estimate: *a §10 target is
an estimate; an implementation's measured worst case replaces it when the difference is explained
by reads, writes or calls the design requires, and the orchestrator accepts it up to +10 %; beyond
that, or for any row in the expedition's path (`play`, the actions sent alone, `enter`, `leave`), it
comes to the project manager.*

## 2. The start hub (E-C)

`create_adventurer` places the adventurer in `START_HUB = 1`, a constant: ENG-03's registry was not
merged. Pillar 6 says core systems read content from registries; §10 already counted one registry
call for `create_adventurer`.

**Recommendation:** once ENG-03 is merged, the start hub is `REGION` 1's town hub, read through
`bundle` (one call, already in §10); **ENG-06** makes the change, since it reads the registry for
every entry. Until then the constant stays, id 1, the test region's town (ENG-03's seed).

## 3. The start town unlocked (E-D)

design/01 lets map travel go "to an unlocked hub" without saying whether the start town counts.
ENG-04 sets its bit.

**Recommendation:** yes, the start town is unlocked from creation: an adventurer can always travel
back to it.

## 4. The cap on adventurer slots (E-F, audit F-3)

ENG-01 §4.5 bounds `set_account_owner` at 7 adventurers (one page of the account's list); design/03
sells more slots than the 3 given (the business model), with no cap. The code loops over the
account's count, correct past 7 but at a cost linear in it.

**Recommendation:** **at most 7 adventurers per account** (3 given, 4 more to buy), enforced where
slots are granted (the future purchase), so that §4.5's bound holds; raise it only with a measured
second page.

to the game orchestrator of that day): **the four recommendations are accepted.**
