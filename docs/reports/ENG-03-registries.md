# [Opus 5.5] ENG-03 — Registries: the store, the content version, a test region

## Summary

The game's content now lives in `Registry` as data. Pull request:
https://github.com/bal7hazar/grimworld/pull/106 (CI green, not merged). The model named in the brief (Opus 5.5) and the model of this session (Opus 5.5, `claude-opus-5-5`) are the same.

- **`Registry`** is implemented; only `upgrade` is still a stub.
  - `set_record(kind, id, record)` checks, in order:
    1. the caller is the administrator (`'not admin'`);
    2. the kind is known (`'registry: unknown kind'`, from `parts`);
    3. the record has exactly `parts(kind)` felts (`'registry: part count'`);
    4. the id is not 0 (`'registry: id zero'`);
    5. part 0 has `LIVE` and no bit above it (`'registry: part 0 not live'`);
    6. the allocation of ids:
       - sequential kinds: the id exists (≤ `last_id`) or is `last_id + 1` (`'registry: id not next'`);
       - `OUTLINE`: the chunk is below 225 or equals 255 (`'registry: outline chunk'`), and the location `id / 256` exists (`'registry: no parent'`);
       - `SHOP`: the hub `id / 16` exists (`'registry: no parent'`);
       - `TASK` and `QUEST`: any non-zero id (see Escalations).
  - **How a change is detected:** each part is compared with the felt already stored. Only the parts that differ are written, and the content version rises by one when any part differs. Writing the same values again writes nothing and leaves the version as it was. A new sequential id reads nothing, because its keys were never written, and always raises the version.
  - Reads:
    - `record`, `records` and `bundle` read records. `records` and `bundle` refuse more than 32 records (`MAX_READ`, `'registry: too many records'`).
    - A record never written reads as `parts(kind)` zeros. Part 0 is then 0, which means the record does not exist.
    - `bundle` returns `(content_version, records in the order asked)`.
    - `content_version()` and `last_id(kind)` are implemented.
  - `set_admin`: only the administrator may call it; it hands the role over and refuses the zero address, as `Hub` does.
  - Cost: a part's address hashes `(kind, id)` once per record and adds one hash per part. The storage layout is unchanged, and a test checks the addresses against the map's own. This cut `bundle` of 32 records from 4,045,220 to 3,477,020 L2 gas (execution).
- **Layouts** are models in `grimworld_logic::models` (D-143, see its section): `REGION`, `LOCATION` (2 parts), `GATE`, and both forms of `OUTLINE`. Each packs into and unpacks from the record's parts through `content::Record`, and has bit-position tests, round trips at the field maxima, and refusals of values wider than their field. They are written into ENG-01 §3.5.
- **Seed data** is in `contracts/seed/test-region.json`, with `README.md` describing it.
  - It holds one region, its town, a zone of 5 chunks with 2 border masks, a dungeon of two floors, and 5 gates: 13 records, 17 slots.
  - `SeedTrait::write(registry)` in `contracts/persistent/tests/test_seed.cairo` writes it through `set_record`. A test reads it back in one `bundle`.

### What is scoped where

- **The record models** are in `contracts/logic/src/models/`. They replace `world.cairo` and its free `pack_*` / `unpack_*` / `outline_id` / `index_fits` functions.
  - `models/index.cairo` holds the four structs together (`Region`, `Location`, `Gate`, `Outline`), with the design's names and the layouts documented on them.
  - Each of `region.cairo`, `location.cairo`, `gate.cairo` and `outline.cairo` holds:
    - `...Impl of ...Trait`, with `new(...)`, plus `Outline::id(location, chunk)` in `outline.cairo`;
    - `...Assert of ...AssertTrait`, the checks `assert_valid`, plus `LocationAssert::assert_index` (a chunk or tile index below 225), which `GateAssert` reuses;
    - `pub mod errors`, with the same messages as before;
    - an impl of `content::Record<T>`.
  - The value constants are scoped in modules:
    - `location::kind::{TOWN … TRIAL}` and `location::biome::{MEADOW … RUIN}`;
    - `gate::kind::{HUB … RIFT}`;
    - `location::INDEX_BOUND` and `outline::CHUNK_SET`.
- **Packing into the record's parts** goes through the new trait `grimworld_logic::content::Record<T>`: `const KIND`, `pack(@T) -> Span<felt252>` and `unpack(Span<felt252>) -> T`. It is the "equivalent into `Span<felt252>`" the rule allows. `StorePacking` does not fit, because the registry stores a record as `parts(kind)` felts under separate keys, not as one struct.
- **`Registry`** (`systems/registry.cairo`):
  - The refusal constants moved into `pub mod errors` (`errors::NOT_ADMIN`, `PART_COUNT`, …).
  - The checks are in `RegistryAssert of RegistryAssertTrait`: `assert_admin`, `assert_record` (kind, part count, id, `LIVE`), `assert_existing`, `assert_parent`, `assert_exists` and `assert_bound`. They run in the same order as before, with the same messages.
  - The address helpers are in `Parts`: `Parts::key`, `address`, `read` and `write`.
  - `InternalImpl` keeps `read_into` and `raise_version`.
  - No signature, storage variable or event changed, and no event was added.
- **The seed helper** (`tests/test_seed.cairo`):
  - `SeedImpl of SeedTrait`: `load()`, `records()`, and `write(registry)`, which is the entry point for later tasks.
  - `WrittenImpl of WrittenTrait`: `add<T, impl R: Record<T>>` appends any model under `R::KIND`, and `write(registry)` writes the records.
  - `Stream` holds the `read_json` cursor, `Row` reads a row as a model (`field`, `location`, `outline`, `gate`), and `Name::short` turns a region name into a short string.
  - `SeedAssert::assert_columns` checks the column names, and `mod errors` holds the messages.
- **The test fixtures** are scoped too: `Fixture` (`deploy`, `version`, `books`) and `Felts` (`live`, `one`, `two`, `three`) in `test_registry.cairo`, `Fixture::deploy` in `test_seed.cairo`, and `Fixture` in `test_models.cairo`.

## Deviations from the brief

- **The verification loop:** I ran the tests of `logic` and `persistent` package by package. The `ephemeral` tests ran in the workspace run of `scripts/gas_budgets.py` (`snforge test --workspace`, through the lock) and in CI, all passing, instead of their own `snforge test`.

- **`is_live` converts part 0 to `u256`**, to split the felt into its limbs as `packing::split` does. The reason is written in the code.

## Escalations

1. **The parent of `TASK` and `QUEST`.** *Resolved by D-145 (1): option (a); see Fix loop 1.* §3.5 says a composite id's parent is "quiver's task or quest". Quiver's records are not in `Registry`, which holds no quiver address. `set_record` therefore accepts any non-zero id for these two kinds. The options are:
   - (a) keep it so;
   - (b) give `Registry` the address of whatever holds quiver's ids, and call it (one call per write, admin-only);
   - (c) make them sequential.

   I recommend (a): only the administrator writes, and a `TASK` or `QUEST` record without its quiver id is inert.
2. **`bundle`'s per-slot cost is not in §9.3–§10.** It is about 36,000 L2 gas per slot read, so a 32-record `bundle` costs 3.48 M in execution. ENG-06 and ENG-07 should add this to every invocation that reads content, on top of the call's C. It is recorded in §3.5; §9.3 and §10 are outside my allowlist.

## Open questions
