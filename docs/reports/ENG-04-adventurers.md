# [Opus 5.5] ENG-04 — Adventurer creation and ownership

## Summary

On `Hub`, a player can now register an account, create and delete adventurers, and hand the account to another owner. Everything follows ENG-01's frozen interface, storage and events; no signature, layout or event changed. Pull request: **https://github.com/bal7hazar/grimworld/pull/100**. CI is green on every job, and `origin/main` (ENG-01b, the ENG-03 brief) is merged in.

- **`register() -> u32`**: one account per address (`account exists`). The record has `slots = 3` (D-33) and every other field 0.
- **`create_adventurer(name, profession) -> u32`**: refusals are `no account`, `empty name`, `bad profession` and `no free slot`. The new adventurer has level 1, rank 0 (Wood) and status `ACTIVE`, and is placed in `START_HUB` (as hub and last hub, with `unlocked` = bit `START_HUB`). Its build is empty with `elite_slot = 255`, its belt and equipment are empty, and its name is the given felt.
- **`delete_adventurer(adventurer_id)`**: the ownership helper runs first. Then "its inventory emptied into the vault" means 4 checks, one read each, with no scan:
  - `core.pack_lanes = 0`: pack balances (`pack holds items`);
  - page 0 of the pack's equipment list is empty, since the list is compact (`pack holds equipment`);
  - `equipped` is empty (`wears equipment`);
  - the pack's gold is 0 (`pack holds gold`).

  The belt only names potion items; the potions themselves are pack balances, so the belt is not checked. The deletion is marked `core.status = DELETED`. The record is never zeroed and the id never reused. The slot is freed by a swap removal in the account's compact list: the last id moves into the hole and the last lane is cleared, while the page keeps `LIVE`.
- **`set_account_owner(account_id, owner)`**: refusals are `not account owner`, `owner is zero` and `owner has an account` (which includes the owner naming itself). It writes the owner word, `account_of[owner] = id`, and `account_of[old] = 0` (E-19). For each listed adventurer that is inside an instance, it calls `Instances.set_controller(adventurer, owner)`. Deleted adventurers are no longer listed, so they are skipped.
- **Views**:
  - `account_of`: 0 when the address has no account.
  - `account`: the owner, the record word as stored, and the ids of adventurers not deleted, in list order.
  - `adventurer`: the 6 stored words (6 zeros for an id never created; a deleted adventurer keeps its words).
- **The ownership helper**, `Hub::InternalTrait::owned_in_hub(adventurer_id) -> (account_id, core word, place word)`, does three reads and refuses once per case: `no adventurer`, `not owner`, `adventurer deleted`, `not in a hub`.
- **Profession ids** are in `grimworld_logic::professions`: `VANGUARD = 1`, `WARDEN = 2`, `ARCANIST = 3`, from design/03's *Professions* table order (D-30), with 0 = none as in every layout. `is_playable` accepts 1–3.
- **Cost** (CAIRO §1): the entrypoints read, check and write the stored words by arithmetic (constant new-adventurer words, `+ONE_ADVENTURER` on the record, lane units, `+DELETED_MARK`) instead of unpacking and repacking. Every constant and helper is pinned against the typed packers in `test_stored_words` (the packers are the oracle, CAIRO §2). The snforge per-call cost fell from 838k to 620k for create and from 728k to 519k for delete (one page).
- The model reports itself as Opus 5.5, which matches the model the brief names.

## Deviations from the brief

- **`set_account_owner` to the zero address is refused** (`owner is zero`). The brief does not list this refusal. It mirrors `set_admin`'s `admin is zero`, since a zero owner would leave the account to nobody and map address 0 to it.
- **Two §9.3 worst cases could not be measured on the local node:** `delete_adventurer` across two pages, and `set_account_owner` with 7 inside. Both need more than 3 slots, or adventurers inside, which no entrypoint of the MVP produces yet; in snforge they are set with `store`. Their node figures above are estimates (E) from the snforge deltas.
- `Instances.set_controller` is exercised only through the double, as the brief asks. The real one (ENG-06) will cost what its own write set says.

## Escalations

- **E-A: `delete_adventurer` is over §10.**
  - Measured: 1,555,840 on the node for one page, and about 1.66–1.70 M (E) for §9.3's two-page row, against a target of 1,150,347.
  - Cause: §10's computation for it is 200,000 (E), but D-33's checks cost reads. The helper takes 3 (core, owner, place), "inventory emptied" takes 3 (the pack's equipment page 0, `equipped`, the pack's gold), plus the record and the list's last page.
  - Already minimal: none of these is unpacked, and a page read once is not read again.
  - Proposal: raise the target to about 1.75 M, or accept it at review. It is a rare action.
- **E-B: `set_account_owner` with 7 inside is over §10** (about 3.4 M (E) against 2,721,351).
  - Per adventurer inside: one `place` read (about 22k) and one call. The double's check-and-write stands in for `I.member` (O).
  - §10 counts 136,000 a call. snforge shows about 214k per adventurer, including the callee's work.
  - Proposal: settle the row when ENG-06 implements `set_controller`.
- **E-C: where the start hub comes from.** `START_HUB = 1` is a constant in `hub.cairo`, used until ENG-03's registry exists. Pillar 6 (core systems read registries) and §10's one registry call for `create_adventurer` suggest it should be `REGION` 1's town hub, read through `bundle`. Please decide whether ENG-03 or a follow-up reads it, and whether the id is 1.
- **E-D: the new adventurer's `unlocked` holds bit `START_HUB`.** design/01 lets map travel go "to an unlocked hub" but does not say whether the start town counts as unlocked; setting its bit seemed the plain reading. Please confirm, or ENG-06 can clear it.
- **E-E: Q-12 and profession ids.** The ids follow design/03's table: Vanguard 1, Warden 2, Arcanist 3, and the Cleric would be 4. Q-12 then decides only which ids `is_playable` accepts, never an id. Q-12 decides no id, so this is noted, not blocking.
- **E-F: accounts with more than 7 adventurers.** ENG-01 §4.5 bounds `set_account_owner` at 7 (one account page). The code loops over the account's list, bounded by its count (≤ its slots), so it stays correct past 7, at a cost linear in the count. Nothing sells slots yet (design/03). Please decide whether buying slots caps at 7 or the bound moves.

## Open questions

- **The vault's panes at registration.** `AccountRecord.vault_panes` is left 0, because the brief asks only for the 3 slots and design/15 says panes "are added by the estate's storehouse". Whether an account starts with one pane of 25 is for the `stow` lot.
- **What "inventory emptied" covers.** Implemented as: pack balances, pack equipment, worn equipment, and pack gold (the belt only names items). If design/03 means the worn equipment may stay on a deleted adventurer, `wears equipment` would go. It is kept as written, since worn items are the adventurer's and would otherwise be lost.
