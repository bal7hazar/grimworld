## Summary

The game now has one geometry layer on `hexx` 0.1.0-rc.1 (D-173), and its trait is frozen for CBT-05a. The model that ran is Opus 5.5 (`claude-opus-5-5`), the model the brief names.

- **The tie rule.** `hexx`'s line follows design/04: at an exact tie it takes the lower tile index. It is held against an oracle written from design/04's sentence alone. Nothing needed wrapping.
- **The vector table** for the client's mirror: `contracts/logic/vectors/window.jsonl`, 2,065 cases since fix loop 3.
- **The per-tick budget line** is in ENG-01 §9.2.

### Optimisations, measured

These were made after a first plain version, with the oracles as the safety net:
- **Arc and facing.** At first they used `hexx`'s `approach`, which costs about 43,500 by itself. They now compute the line's first step in constant time with the same rule, which brought the arc at range from 55,826 and on the ring from 106,576 down to 25,240.
- **Facing at range:** 53,626 → 22,500.
- **Interior `DISC_1` and `RING_1`.** They are now one field product with a constant relative mask, hexx's `neighbor_mask` written out for the width 15.
- **`tiles`.** The lowest set bit is read from a table at `2^p mod 131` (94,874 → 57,151 for 7 tiles).

## The rules and the frozen signature (AC-2, AC-3)

Positions are the window's index `15 y + x` (`hexx`'s layout: pointy-top, odd-r, `+1` West, `+15` North), 0 to 239. A facing is `0..=5`: East, North-East, North-West, West, South-West, South-East (`actions`, `hexx::board::direction::Direction`).

```cairo
// grimworld_logic::types::window
pub const WIDTH: u8 = 15; pub const HEIGHT: u8 = 16; pub const SIZE: u8 = 240;
pub mod range { TOUCH = 1, NEARBY = 2, AREA = 3, ALERT = 5, RANGED = 6, EARSHOT = 8 }  // u8
pub mod errors { OPEN = 'window: open above 240', FACING = 'window: facing', SHAPE = 'window: shape' }

pub const FAR: u8 = 255;                                           // the distance of a position outside (fix loop 3)

#[derive(Copy, Drop, PartialEq, Debug)]
pub struct Window { open: felt252 }   // private (fix loop 3): bit p = 1, tile p walkable; bits ≥ 240 are 0
pub impl WindowSerde of Serde<Window>;   // one felt; deserialize refuses (None) a bit ≥ 240

pub trait WindowTrait {
    fn new(open: felt252) -> Window;                               // asserts no bit ≥ 240
    fn inside(position: u8) -> bool;
    fn open(self: @Window) -> felt252;                             // the walkable bitmap (fix loop 3)
    fn distance(from: u8, to: u8) -> u8;                           // hex distance, walls ignored; FAR outside
    fn sight(self: @Window, from: u8, to: u8) -> bool;
    fn reach(self: @Window, from: u8, to: u8, range: u8) -> bool;  // distance ≤ range && sight
    fn arc(source: u8, target: u8, facing: u8) -> Option<Arc>;     // facing: the target's
    fn front(source: u8, target: u8, facing: u8) -> bool;          // facing: the source's (fix loop 1)
    fn facing(from: u8, to: u8, facing: u8) -> u8;                 // the facing after the action
    fn shape(self: @Window, shape: u8, centre: u8) -> felt252;     // effect::shape ids 1–5
    fn tiles(mask: felt252) -> Span<u8>;                           // ascending
}
pub trait WindowAssertTrait {
    fn assert_valid_open(open: felt252);
    fn assert_valid_shape(shape: u8);
    fn direction(facing: u8) -> hexx::board::direction::Direction;  // fix loop 2: was `facing`
}
// Arc: grimworld_logic::types::combat::Arc { Front, FrontSide, RearSide, Back } (as in #229)
```

### The rules

- **`sight`.** The fixed integer hex line. Walls block and actors do not (an actor is not in `open`). Since fix loop 1, a wall at either end blocks too. At a tie, the lower tile index. This is `hexx`'s `LineTrait::line` plus the two ends, checked against `open`.
- **`reach`.** The target of an action: within its range and in sight. Touch is never blocked, since adjacent tiles have nothing between them. A radius that needs no sight (alert, earshot) is a `distance`.
- **`arc`.**
  - The arc of the target's facing the hit arrives from: the source's tile when adjacent; at range, the tile the line of sight arrives from.
  - The line is symmetric, so that tile is the first step of the line from the target. It is computed in constant time by the line's rule (`WindowInternal::step`): an axis of largest magnitude moves; of the two others, the larger moves; at a tie, the lower tile index. Then design/04's arcs: `d` front, `d ± 1` front-side, `d ± 2` rear-side, `d + 3` back.
- **`front`.** Whether the target stands on the source's front tile (Blind, §5.6).
- **`facing`.** §5.3 step 3: toward the moved-to tile or the target; for a target not adjacent, the direction of the first step of the hex line.
- **`shape`.**
  - `SINGLE`, `RING_1`, `DISC_1`, `DISC_2`, `DISC_3` by hex distance from the centre.
  - The result is a bitmap whose order is the ascending tile index of the executor's actor list (§5.14 step 4).
  - A tile outside the window is skipped. Walls hold no actor and are skipped.

### Edges (D-140), all tested

None of these panics:
- **A position outside the window:** no sight, no reach, no arc, not in front, the facing unchanged, an empty shape.
- **The same tile:** in sight, no arc, not in front, the facing unchanged.
- **A line leaving the window** (at the East edge the lower index can be the column −1): no sight, as a wall (`hexx` D-27). The arc and the facing are still the first step's direction, which needs no board.
- **A wall at either end of the line:** no sight (fix loop 1, `test_sight_wall_at_an_end`).

These two panic: a facing above 5 and a shape id outside 1–5 (stored values the pipeline refuses), with `errors::FACING` and `errors::SHAPE`.

### Tests (in the module, D-167)

- **`test_line_against_oracle_centre` and `_edges`.**
  - For every pair within distance 2 to 6 from both row parities at the centre, and from 8 edge and corner tiles, `hexx`'s line equals design/04's line both ways. `Oracle::line` takes the nearest tile by its hexagonal cell and resolves ties to the lower index.

- **`test_line_ties`.** The tie cases named one by one: a tie on a row and across two rows, both orders, distances 2, 4 and 6, a wall on the chosen tile against a wall on the other, a tie at the edge leaving the window.

## Escalations

1. **Shared and design files still name `origami_hexmap`.** All are outside my allowlist, for the orchestrator:
   - `CONTEXT.md` (8 mentions).
   - `docs/CAIRO.md`: the intro ("the map library `origami_hexmap` is the reference") and §4 ("`u252` from `origami_hexmap`"). `hexx` 0.1.0-rc.1 has no `u252` type; it handles bitmaps as `felt252` and `u256` through `Bits`. No game code uses `u252`, so §4's rule needs rewording.
   - `docs/briefs/COMMON.md` §1 (the same `u252` rule).
   - `docs/design/02-core-loop.md` (the *Library* row).
   - `docs/design/04-combat.md`: "This function is not part of `origami_hexmap` and is ours to write". Line of sight is now `hexx`'s N-5, and the game's tie rule is checked against it.
   - `client/app/src/input/coords.ts` (a comment).
   - `indexer/emitter/Scarb.lock`: a separate workspace, IDX-01's (track CV, D-149), not touched.
2. **The tie rule depends on orientation.** Design/04's "lower tile index" holds on the window's index (`15 y + x`) as on the global tile (`x + 256 y`) only while the window's axes run the same way as the location's. ENG-07's assembly must keep that orientation, or the mirror and the contract would disagree at ties.
