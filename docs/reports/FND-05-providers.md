# [Opus 5.5] FND-05 — Provider interfaces

## Summary
The game's two provisional providers now sit behind interfaces. They are ready and tested, and no game system uses them yet. The session ran as Opus 5.5, the model the brief names.

- **Contracts.**
  - `grimworld_logic::fate` holds three things:
    - `derive(word, domain, index) = poseidon(word, domain, index)` (ADR-0002 rule 2);
    - `domain(subject, counter, purpose) = poseidon(subject, counter, purpose)` (ENG-01 §7);
    - eight distinct purposes, one per use of Fate: `ENTRY`, `LOOT`, `CHEST`, `IDENTIFY`, `LIFT`, `BREW`, `HINT`, `RIFT_BOARD`. Each is tested distinct.
  - `Hub` and `Instances` now implement `set_contracts` and `set_admin`, and only the administrator may call them. `set_admin` hands the role over.
  - `upgrade` is still a stub, and `TxHashFate` is unchanged.
- **Client.** `client/app/src/account/` holds:
  - the `AccountProvider` interface (`createOrRestore`, `execute`, `status`, `signOut`), with types of its own;
  - a **burner** implementation on starknet.js. It generates a key and keeps it in the device's storage. The game deploys the account through the universal deployer and funds it, using a pre-funded account of the local node behind a `Funder` port. Executions are sent one at a time, with no prompt.
  - The chain library is imported only by `starknet.ts`, and a TypeScript-checker test shows that no exported type reaches it.
  - Tested by unit tests on a fake chain, plus one integration test against the real local node.
- Pull request: https://github.com/bal7hazar/grimworld/pull/92. CI is green on every job (client, cairo contracts, spikes, tooling). Not merged.

## Acceptance criteria
- **AC-1** `fate` is deterministic per transaction and domain, and `derive` gives distinct values per domain and index. Shown by:
  - `test_fate_deterministic_per_transaction_and_domain`: same tx and domain give the same word; another purpose, sequence or transaction gives another word.
  - `test_fate_values_distinct_through_derive`: 8 purposes × 4 indices from the deployed provider, all distinct.
  - `grimworld_logic::test_fate::*`: the oracle, 41 values distinct, the fuzz test, purposes and domains distinct.
  
  Every test has a budget.
- **AC-2** The provider is refused on mainnet at deployment and at call time: `test_fate_refuses_mainnet_deployment` and `test_fate_refuses_mainnet_calls` (ENG-01's, still passing, unchanged).
  - **Where the check lives, and why it cannot be skipped.** It is in two places in `TxHashFate` (`fate.cairo:23` and `:31`): the constructor, and the body of `fate` itself. The chain id comes from `get_tx_info`, which the sequencer sets; the caller cannot choose it.
  - The constructor check alone could be bypassed. The class could reach mainnet code without running a constructor, through `replace_class_syscall` into an existing contract or through `library_call` from another contract.
  - The call-time check cannot be bypassed. Every path to a word runs through the body of `fate`, and the chain id is checked there before the hash is read. So even this class declared on mainnet and reached another way refuses to draw.
- **AC-3** The provider's address can only be set by the administrator. Shown by:
  - `test_hub_set_contracts_by_admin`, `test_hub_set_contracts_refused_to_others`, `test_hub_set_admin_hands_over` (the former admin is refused afterwards and cannot take the role back), `test_hub_set_admin_refused`;
  - the same four for `Instances`;
  - `test_fate_at_the_configured_address`: the address set in `Hub` is the provider called.
  
  The address is never hard-coded: it comes from the constructor and from `set_contracts`. The `grep` above shows that only `systems/fate.cairo` reads the transaction hash.
- **AC-4** The account provider's four operations work against the real local node: `burner.node.test.ts` via `scripts/with-node.sh`. It covers create (deployed and funded), one call that writes (`approve`) reaching `succeeded`, a refused call rejected as `refused`, sign out (`execute` then gives `not-ready`), and restore from the device's storage by a new provider (same address; it sends again). No vendor type is exported: `vendor.test.ts`.
- **AC-5** No prompt, no fee, and no blockchain word reach the player:
  - `execute` signs with the kept key and never prompts.
  - Nothing in the interface concerns fees.
  - The four `AccountError` messages are neutral and tested against a list of forbidden words ("what a player could see"). The vendor's messages stay in `cause`, never in `message`.

## Deviations from the brief
- **Names.** `IRandomness` is `IFate`, as frozen by ENG-01 (the brief's amendment). `Call` is the module's own type, `{ to, entrypoint, calldata }`. `AccountHandle` is `{ address }`. `ExecutionId` is a branded string. `ExecutionStatus` is `pending | succeeded | failed | unknown`: a pre-confirmed execution still reads `pending` unless it reverted. RPC 0.9 and later have no rejected status, so a call the node refuses rejects `execute` with `refused` instead.
- **`domain(subject, counter, purpose)`.** This helper is added next to `derive`. It is ENG-01 §7's composition, so that every future draw builds its domain the same way.
- **`RIFT_BOARD` purpose.** Added from design/17 (*On-chain*: the day's board comes from one Fate draw). There is no purpose for a chunk reveal: under D-111 a reveal is computed from the entry draw, not drawn.
- **`set_admin` refuses the zero address** (`'admin is zero'`). Handing the role to nobody would leave `set_contracts` and `upgrade` unusable forever. The brief does not ask for this; it is a guard, not a game rule, and it is tested.
- **The burner's account class on the local node is OpenZeppelin v1.0.0** (`0x05b4b537…3564`), which starknet-devnet 0.10 declares at start. D-137's `AccountUpgradeable` v3.0.0 (`0x01d1777d…2381`) is not declared there. The class is configuration (`accountClass`), and both classes take the public key as their only constructor argument.
- **`signOut` ends the session but keeps the key on the device.** That is what makes the brief's "sign out, restore" restore the same account; deleting the key would lose the account (ADR-0005 §3). See *Open questions*.
- **Deployment.** The funder deploys the account through the universal deployer and funds it with 10 STRK, in one execution. It does not use SPK-1b's `DEPLOY_ACCOUNT` by the burner itself. This matches "an account deployed by the game" and needs no first transaction from the burner.
- **`vendor.test.ts` imports `typescript`** from the root devDependencies (it resolves from `client/app`), so no dependency or lockfile change was needed.
- The branch has one merge commit from `origin/main` (docs only, #90 and #91), with git's default message and no trailer.

## Escalations
- **The doc comment of `IFate` is inaccurate** (`contracts/logic/src/interface.cairo`, outside my allowlist). It says "derives them as `poseidon(word, index)`", but ADR-0002 rule 2 and `derive` use `poseidon(word, domain, index)`. The fix is a one-word comment change by whoever owns the file.
- **The funder on a public network.** `createNodeFunder` holds a signing key in the client, which is acceptable only with the local node's pre-funded key. On Sepolia the funder has to be a service of the game behind the same `Funder` port, and the key must never ship in the client. This needs a brief (and COMMON §4's sending rules).
- **The class hash on Sepolia and mainnet.** D-137's burner class is declared on Sepolia; ADR-0005 notes it is unmeasured whether it exists on mainnet. The class is configuration, so nothing in the code changes; this is just noted.

## Open questions
- **Should `signOut` forget the key?** On a shared device, keeping it means the next person restores the same burner. Forgetting it loses the account and everything it owns (ADR-0005 §3). I chose to keep it. A separate "forget this device" operation would be a fifth operation outside ADR-0005 §1, so I did not add one.
- **Funding amount and top-ups.** 10 STRK per burner on the local node is arbitrary but harmless. Top-ups when a burner runs low are not designed yet (D-137 says the game funds, not how often).

### F-1 (major): the funder refused anything but the local node, in code
- **Where:** `client/app/src/account/starknet.ts`, in `assertLocalNode` and `createNodeFunder`. `provide` runs the check first, every time. The signing `Account` is only built after the check passes, so nothing is signed or sent before it.
- **Checks, in order:**
  1. The endpoint must be on this machine (`127.0.0.1`, `localhost` or `[::1]`, over http or https). Anything else is refused before any request.
  2. The node must answer `devnet_getPredeployedAccounts`, a method only the local node has, and its list must contain the funder's address **with the same private key**.
  3. The chain id must not be `SN_MAIN`.
- **Why check 2, and why configuration cannot get past it.**
  - The chain id cannot tell the local node from Sepolia: starknet-devnet reports `SN_SEPOLIA`.
  - A loopback URL alone can be a tunnel to a public node.
  - Configuration supplies only an endpoint, an address and a key. The funder will only sign with the account and key that a node on this machine publishes as its own pre-funded account, over the endpoint it then sends to. *(Corrected in fix loop 2: an earlier sentence here said such a key "holds nothing of value on any network". That was too absolute, because anyone can fund that account elsewhere. The protection is the enforced local-node boundary, not the key's worth.)*
  - Getting past this takes a program written to impersonate the local node's methods, not a setting.
  - The funder's traffic all goes through one `fetch`, now injectable, so tests can see every request.
- **Failure mode:** a refusal raises `LocalNodeRefused` (exported). The burner wraps it as `AccountError("unavailable")`, so the player-facing message stays neutral.
- **Public networks:** funding there is still a server-side `Funder`, out of this task.
- **Tests, offline** (`starknet.test.ts`, 11 cases, fake `fetch` recording every method):
  - Six endpoints off this machine are refused **before any request**: Sepolia and mainnet RPCs, a LAN IP, `127.0.0.1.example.com`, a `ws:` URL, and a non-URL.
  - A loopback endpoint without the devnet method (a tunnel) is refused after that single request.
  - An unpublished funder address is refused.
  - A published address with another key (a key of value) is refused.
  - Mainnet's chain id is refused.
  - In none of these refusals is any signing or sending method reached (`addInvokeTransaction`, `estimateFee`, `getNonce`, …).
  - The pass case: `localhost` with the published funder goes past both checks and signs nothing for an account that already exists.
- **Against the real node:** the integration test passes, with the funder using the node's published key.

### F-2 (major): sign-out cancels a pending open
- **Where:** `client/app/src/account/burner.ts`.

  - The preparation (deployment check, funding) is shared and runs to the end, across a sign-out too. The key and the account stay kept, and an open asked after the sign-out joins the same preparation instead of funding twice.
  - An execution still waiting its turn when the player signs out is not sent (`not-ready`).
- **Tests** (`burner.test.ts`):

  - "an execution waiting for its turn is not sent after the sign-out".
  
  Each holds the step pending with a gate, signs out, then releases the step. The first two check that `execute` refuses and nothing is sent.

### F-3 (major): no trusted `ready` flag; the record is bound to its network and class
- **Where:** `client/app/src/account/burner.ts` (`prepare`), plus `BurnerChain.binding()` in `starknet.ts`, which returns the chain id and the account class.

  - Under another binding (another network or class), the key is kept, the address is derived again and the record rewritten. A v1 record keeps its key.
  - A session already open in memory is not re-checked.
- **Tests:**
